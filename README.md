# Прогноз валидаций трамвайных маршрутов

## Производительность (измерено 27 сентября 2026)

Нагрузочный тест выполнен на **отдельном дубликате backend-контейнера** с лимитами **2 vCPU / 2 ГиБ RAM, swap отключён**. Исходный экземпляр продолжал работать. На тестовом экземпляре отключена авторизация; PostgreSQL и model остались общими с исходным Compose. Генератор k6 находился в отдельном контейнере; Docker Desktop: 16 логических CPU и 7,35 ГиБ памяти. Каждый запрос возвращал один часовой прогноз по `demo-1`; проверялись HTTP 200, `is_mock=false` и наличие прогнозного значения. Один прогон длился 30 секунд, кроме 200 RPS (40 секунд). Целевые условия: p95 < 300 мс, < 1% ошибок, 0 пропущенных итераций.

| Сценарий | Задано | Достигнуто | p95 | Ошибки / пропуски | CPU и RAM | Итог |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| Готовый прогноз 2025, PostgreSQL | 60 RPS | 59,96 RPS | **48 мс** | 0 / 0 | backend 93–98% CPU (46–49% лимита), 73–74 МиБ | Выполнено на этом сценарии |
| Готовый прогноз 2025, PostgreSQL | 80 RPS | 79,94 RPS | **59 мс** | 0 / 0 | backend 119–135% CPU (60–68% лимита), 74–75 МиБ | Выполнено на этом сценарии |
| Готовый прогноз 2025, PostgreSQL | 100 RPS | 96,03 RPS | **1 297 мс** | 0 / 38 | backend около 200% CPU (лимит 2 vCPU), 76–77 МиБ | Не выполнено |
| Готовый прогноз 2025, PostgreSQL | 200 RPS | 92,76 RPS | **7 142 мс** | 0 / 3 840 | backend около 200% CPU, 73–78 МиБ | Не выполнено |
| Новые даты 2027 через LightGBM, без прогретого кэша | 2 RPS | 2,00 RPS | **203 мс** | 0 / 0 | backend 73 МиБ; model около 127 МиБ | Выполнено на этом сценарии |
| Разные будущие даты 2026 через LightGBM | 10 RPS | 7,25 RPS | **8 556 мс** | 0 / 24 | model около одного ядра CPU, 120–142 МиБ | Не выполнено |

`docker stats` показывает 100% CPU как одно ядро; для лимита в два ядра 200% означает полную загрузку. Во время теста архивного прогноза при 80 RPS память backend оставалась в диапазоне 74–75 МиБ, а `memory.swap.current` после прогонов был **0** у backend и model. Эти короткие прогоны не доказывают долгосрочную стабильность памяти. ML-сервис и PostgreSQL работают в **отдельных контейнерах**: результат 80 RPS не является подтверждением для решения «всё в одном контейнере». В API сейчас нет endpoint для приёма потоковых событий, поэтому эта часть требования не измерена. Общий критерий «сотни RPS при p95 < 200–300 мс в одном контейнере» **пока не выполнен**.

Воспроизведение: сценарий [bench/forecast.k6.js](bench/forecast.k6.js), сырые [результаты k6 и замеры ресурсов](bench/). После запуска Compose выполните из корня репозитория (в PowerShell `${PWD}` можно использовать в указанном виде):

```sh
docker build -f backend/Dockerfile -t hackaton-asumadi-bench-backend:local .
docker run -d --name hackaton-asumadi-bench-backend --network hackaton_asumadi_default --cpus 2 --memory 2g --memory-swap 2g --env-file .env -e CATALOG_BACKEND=postgres -e DB_HOST=db -e DB_PORT=5432 -e MODEL_SERVICE_URL=http://model:8080 -e AUTH_ENABLED=false -p 127.0.0.1:8001:8000 hackaton-asumadi-bench-backend:local
docker run --rm --network hackaton_asumadi_default -v "${PWD}/bench:/bench" -e BASE_URL=http://hackaton-asumadi-bench-backend:8000 -e WORKLOAD=archive -e RATE=80 -e DURATION=30s grafana/k6:latest run /bench/forecast.k6.js
```

Для новых дат используйте `WORKLOAD=future-cold` и `RATE=2`; повторный прогон тех же дат уже измеряет прогретый кэш. Для мониторинга: `docker stats hackaton-asumadi-bench-backend hackaton_asumadi-model-1`. Методика фиксированной интенсивности и порогов взята из [документации k6](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/) и [порогов k6](https://grafana.com/docs/k6/latest/using-k6/thresholds/); трактовка CPU и памяти — из [документации Docker](https://docs.docker.com/reference/cli/docker/container/stats/).

Веб-приложение показывает прогноз числа пассажирских валидаций для девяти трамвайных маршрутов Москвы. Для обычного запуска нужен только Docker с Compose. Python и Node.js на компьютере устанавливать не требуется.

## Запуск

1. Установите и запустите Docker Desktop (или Docker Engine с Compose v2).
2. Откройте терминал в корне репозитория и выполните:

   ```bash
   docker compose up -d --build --wait
   ```

3. Откройте [http://localhost:5173](http://localhost:5173). Демо-вход: `dispatcher` / `tram2026`.

При первом запуске Docker скачает образы, соберёт frontend, backend и модель, создаст базу и заполнит её встроенными данными. Следующие запуски выполняются той же командой. Приложение использует четыре постоянно работающих контейнера:

| Контейнер | Для чего нужен |
| --- | --- |
| `db` | PostgreSQL с каталогом маршрутов и остановок |
| `backend` | API и выдача готового прогноза модели |
| `model` | Инференс сохранённых LightGBM-моделей для новых дат; доступен только внутри сети Compose |
| `frontend` | Собранный сайт и прокси запросов к API |

Код и артефакты модели лежат в `tram_final/tram_final/`, исходная почасовая история — в `data/labels/`. За **1 ноября — 31 декабря 2025 года** backend отдаёт точный итоговый прогноз команды из `tram_final/tram_final/outputs/submission_final.csv`. Для дат **2026–2027 годов** контейнер `model` рассчитывает новый маршрутный прогноз сохранёнными LightGBM-бустерами по истории до 31 октября 2025 года. Это экстраполяция ML-компонента без математического финального ансамбля; её точность на фактических данных 2026–2027 годов не проверена. Годовой режим и прогноз по отдельным остановкам пока недоступны. Подробности — в [описании интеграции модели](docs/tram-final-integration.md).

## Карта Яндекса

Если нужен фон Яндекс Карт, скопируйте `.env.example` в `.env` в корне репозитория и укажите в нём `VITE_YANDEX_MAPS_API_KEY`. Затем пересоберите frontend:

```bash
docker compose up -d --build --wait frontend
```

Без ключа приложение работает со схематической картой. Ключ попадает в браузерную сборку, поэтому настройте для него ограничение по домену в кабинете Яндекса и не добавляйте `.env` в Git.

## Проверка и управление

```bash
docker compose ps                 # состояние контейнеров
docker compose logs -f backend   # журнал API, Ctrl+C для выхода
docker compose logs -f model     # журнал модели
docker compose down              # остановить, сохранив данные PostgreSQL
```

После обновления кода снова выполните `docker compose up -d --build --wait`. Для чистого повторного запуска данные базы удалять не требуется. Команду `docker compose down -v` используйте только если намеренно хотите удалить локальную базу.

Служебный `schedule-import` не запускается вместе с сайтом. Он нужен только для ручной загрузки архивного расписания остановок:

```bash
docker compose --profile tools run --rm schedule-import
```

Если порт `5173`, `8000` или `55432` занят, освободите его и повторите запуск. API доступен на [http://localhost:8000](http://localhost:8000), проверка готовности — [http://localhost:8000/health/ready](http://localhost:8000/health/ready). Для обычной работы открывайте сайт на порту `5173`.

## Состав репозитория

`frontend/` — интерфейс React; `backend/` — FastAPI; `model_service/` — контейнер инференса; `tram_final/tram_final/` — исходники, артефакты и результат модели; `data/labels/` — агрегированная история валидаций; `db/` — схема и начальные данные PostgreSQL; `docs/` — архитектура, контракт API и сведения о модели. Сырые `data/train.csv` и `data/test.csv` весят около 10 ГБ и в Docker-образ не копируются. Демо-учётная запись в `mock_data/dispatchers.json` предназначена только для локального запуска.
