# Прогноз пассажиропотока трамваев

Стартовый mono-repo для Хакатона Московского транспорта 2026. Реализованы архитектура и контракт ML ↔ Backend, конфигурируемый каркас FastAPI, PostgreSQL, повторяемый demo seed и локально запускаемый React.

Приложение показывает **демонстрационный прогноз** из backend: можно выбрать трамвайный маршрут, участок между двумя остановками одного направления, дату и горизонт. География 36 маршрутов с присланной схемы трамваев Москвы взята из снимка OpenStreetMap; `predicted_load` остаётся синтетическим индексом, не количеством пассажиров и не процентом заполнения.

Основной документ: [архитектура и контракт](docs/architecture.md). Примеры [request](docs/examples/forecast-request.json) и [response](docs/examples/forecast-response.json). Результаты проверок и ограничения: [verification.md](docs/verification.md).

DB-задача: [подробная схема, запуск и тесты](docs/db.md),
[подтверждённый Docker-прогон](docs/db-verification.md) и
[инструкция отправки на ревью](docs/github-db-review.md).
В Compose сохранён внешний порт команды **55432**; backend внутри Docker использует `db:5432`.

Схема взаимодействия и принятые ограничения подробно описаны в `docs/architecture.md`. География маршрутов взята из OSM, но её полнота и актуальность не гарантируются; реальные данные пассажиропотока и обучение модели пока не входят в текущий каркас.

## Demo seed

Набор содержит 36 маршрутов, 2132 остановки-площадки по двум направлениям,
2132 связи направлений и 52032 почасовых демопрогноза с разными уровнями
загрузки, утренним и вечерним пиками. Координаты остановок и геометрия путей
взяты из отношений маршрутов OpenStreetMap, а **все значения загрузки вымышлены**.
Маршрут 6к построен как укороченный участок OSM-маршрута 6 от Братцева до
Восточного моста. У отдельных направлений OSM названия конечных отличаются
от схемы (например, «15-я Парковая улица»/«Восточное Измайлово»), хотя
площадки расположены рядом. Снимок следует проверять перед использованием
как актуального транспортного справочника.

После запуска PostgreSQL одна команда повторяемо наполняет БД:

```bash
docker compose exec -T db sh /opt/transport/db/scripts/manage.sh seed
```

Проверить количество строк:

```bash
docker compose exec -T db sh /opt/transport/db/scripts/manage.sh status
```

Исходники seed находятся в `db/seed/`; `mock_data/catalog.json` используется
backend без PostgreSQL. Повторно сгенерировать каталог и SQL из закреплённого
снимка `mock_data/osm_trams.json` можно командой
`python db/seed/generate_seed.py` из корня проекта.
В обычном запуске сеть для генерации seed не нужна. Для отдельного обновления
географии из OSM есть `python db/seed/import_osm_trams.py`; перед таким
обновлением нужно проверить актуальность маршрутов и заново выполнить тесты.

## Карта и фильтры

Frontend получает маршруты, остановки, временной ряд и срез загрузки через
`/api/routes`, `/api/routes/{route_id}/stops`, `/api/routes/{route_id}/geometry`, `/api/forecast` и
`/api/forecast/map`. Изменение маршрута, пары остановок, горизонта, даты или времени
автоматически обновляет карту и график. Без пары остановок показан весь маршрут;
после выбора «От» и «До» — соответствующий участок пути OSM и его остановки.
«До» можно выбрать только ниже по тому же направлению. Нажатие на маркер
заполняет поле «От». В режиме участка график показывает прогноз у начальной остановки,
а не сумму загрузки по всему отрезку.
Для суточного горизонта можно задать диапазон часов и минут `[с, до)`, например 07:25–11:43;
интерфейс запрашивает точки с шагом **1 минута** (`resolution=PT1M`). Для других клиентов
API прежний шаг `PT1H` остаётся значением по умолчанию. Seed БД хранит почасовой снимок;
минутные значения вычисляет mock predictor по запросу, это не реальные наблюдения.
Цвет маркера и отрезка линии соответствует демопрогнозу на начало диапазона.
Для месяца/года карта показывает первый интервал выбранного периода.

`mock_data/service_hours.json` содержит лишь условное окно движения 5:00–1:00 МСК.
Оно не учитывает реальные отправления, направление, день недели и временные изменения.
Для настоящего расписания нужен разрешённый машиночитаемый источник и сопоставление
его ID остановок с каталогом OSM. [Официальный портал расписаний Москвы](https://transport.mos.ru/transport/schedule)
подходит для проверки вручную; открытый фид для автоматической загрузки в этом проекте пока не подтверждён.

Для отображения карты обязателен `VITE_YANDEX_MAPS_API_KEY`; используется только подложка Яндекс Карт.
При отсутствии ключа или ошибке загрузки интерфейс показывает ошибку и не переключается на другую карту. Геометрия линий,
остановки и прогноз поступают из нашего backend API. Цвет каждого участка
берётся от демопрогноза ближайшей остановки, то есть не измеряет фактическую
загрузку на путях. Подложка Яндекс Карт требует интернет-соединения.

Ключ для локального Vite положите в `frontend/.env.local`, а для Docker Compose —
в корневой `.env` как `VITE_YANDEX_MAPS_API_KEY=...`. Эти файлы исключены из Git.
Для опубликованного сайта задайте ту же переменную **во время сборки frontend**
в настройках хостинга; один `git push` не передаёт локальный ключ на сервер.
Браузерный ключ виден в сетевых запросах, поэтому ограничьте его по HTTP Referer
для локального и рабочего доменов в кабинете Яндекса. API v3 требует такое
ограничение. Настоящий ключ нельзя помещать в `.env.example` или в коммит.

Геоданные: © [OpenStreetMap contributors](https://www.openstreetmap.org/copyright),
[ODbL 1.0](https://opendatacommons.org/licenses/odbl/1-0/). Источник закреплён
в `mock_data/osm_trams.json` с ID отношений OSM. Маршруты и остановки нужно
сверять с текущими официальными схемами — OSM может отставать от изменений.
[Страница Московского трамвая](https://mosmetro.ru/tram) и
[официальная схема](https://mosmetro.ru/static/etp-new/docs/trammap/trammap_15_04_26.pdf)
служат справочным материалом, а не источником координат в seed.

## 1. Получить рабочую копию

Для командной работы клонируйте общий репозиторий:

```bash
git clone https://github.com/hlpne/hackaton_asumadi.git
cd hackaton_asumadi
```

Для просмотра незамерженной задачи перейдите в соответствующую ветку команды.
Распакованный архив можно запускать отдельно, но для отправки изменений используйте
клон репозитория и патч. Повторный `git init` и загрузка `.bundle` в репозиторий не нужны.

## 2. Требования

- Python **3.12**.
- Node.js **22.12+** и npm; проверка выполнена на Node 24.
- Git — для клонирования.
- Docker с Compose v2 — только для режима с контейнерами.
- Для первой установки Python/npm-пакетов и загрузки Docker-образов нужен доступ к соответствующим реестрам.

После установки зависимостей прогноз и каталог не обращаются к внешним сервисам. Подложка загружается через API Яндекс Карт, Swagger UI использует внешние CDN-ресурсы; без сети API и прогноз продолжают работать, но карта не отображается.

## 3. Локальный запуск без Docker и PostgreSQL

Это самый короткий способ проверить проект. Каталог читается из `mock_data/catalog.json`, прогноз возвращает Mock Predictor. `/health` сообщает `database: "disabled"`.

Откройте **два терминала** в корне рабочей копии. Создайте `.env` из примера один раз.

### Windows PowerShell

Терминал 1:

```powershell
Copy-Item .env.example .env
cd backend
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Активация окружения не требуется, поэтому менять ExecutionPolicy не нужно. Если `py` не установлен, используйте `python` после проверки, что это Python 3.12.

Терминал 2:

```powershell
cd frontend
npm ci
npm run dev
```

### Linux или macOS

Терминал 1:

```bash
cp .env.example .env
cd backend
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Терминал 2:

```bash
cd frontend
npm ci
npm run dev
```

Откройте [приложение](http://localhost:5173), [Swagger](http://localhost:8000/docs) или [readiness check](http://localhost:8000/health). Выберите маршрут, остановку и период: карта, график и таблица обновятся автоматически. При ошибке API интерфейс показывает ошибку, а не подменяет ответ браузерными mock-данными.

Каркас предоставляет три диагностических endpoint:

- `/health/live` — процесс FastAPI работает; внешние зависимости не проверяются;
- `/health/ready` — приложение готово обслуживать запросы; при PostgreSQL выполняется `SELECT 1`;
- `/health` — совместимый alias readiness-проверки из исходной задачи.

Ответ health содержит имя и версию сервиса, окружение, режим каталога и состояние БД. При недоступной PostgreSQL readiness возвращает 503 в общей структуре ошибок, а liveness остаётся доступным.

API прогнозов:

- `/forecast` — временной ряд одного маршрута/остановки;
- `/forecast/map` — географический срез по всем или выбранному маршруту на заданный момент;
- `/forecast/top-overload` — детерминированный Top-N точек по `predicted_load`.

Для map и Top-N доступны `horizon`, `timestamp`, `forecast_origin`, `route_id` и `direction_id`; у Top-N также есть `limit` от 1 до 50. Без параметров используются стабильные demo-значения. Слово `overload` в URL не означает, что уже известна вместимость: до получения официального target endpoint только ранжирует нейтральный показатель нагрузки.

Месяц и год начинаются с первого числа выбранного месяца; сутки — с выбранной даты. Для года возвращаются 12 месячных интервалов, для месяца — дневные, для суток — часовые.

Остановка локальных серверов: `Ctrl+C` в каждом терминале. При повторном запуске окружение и зависимости заново создавать не нужно.

## 4. Запуск всех компонентов через Docker Compose

Из корня проекта, после создания `.env`:

```bash
docker compose up --build
```

Frontend: [localhost:5173](http://localhost:5173), backend: [localhost:8000/docs](http://localhost:8000/docs). Compose задаёт `CATALOG_BACKEND=postgres` для backend независимо от локального `CATALOG_BACKEND=memory` в примере `.env`. Данные БД сохраняются в volume.

Остановить контейнеры, сохранив данные:

```bash
docker compose down
```

Начальная схема и seed применяются автоматически только при создании пустой БД.
Порядок обновления без удаления данных — в [docs/db.md](docs/db.md).
Запуск PostgreSQL 16.15, сохранность данных после restart и SQL-проверки подтверждены
участником; подробности и границы проверки — в [отчёте](docs/db-verification.md).

## 5. Локальные приложения с PostgreSQL в Docker

Из корня:

```bash
docker compose up -d db
```

В `.env` установите `CATALOG_BACKEND=postgres`, `DB_HOST=127.0.0.1`,
**`DB_PORT=55432`** и согласованные `POSTGRES_*`. Это порт подключения с компьютера
к контейнеру в текущей конфигурации команды. Внутри Compose backend продолжает
использовать `DB_PORT=5432`. Запустите backend/frontend командами из раздела 3.
`/health` и `/health/ready` должны вернуть `database: "ok"`.

Основные backend-настройки собраны в корневом `.env`: `APP_NAME`, `APP_VERSION`, `APP_ENV`, `LOG_LEVEL`, `CATALOG_BACKEND`, `PREDICTOR_FACTORY`, `DB_HOST`, `DB_PORT`, `POSTGRES_*`, `DB_CONNECT_TIMEOUT` и `DB_STATEMENT_TIMEOUT_MS`. Числовые таймауты и допустимые значения проверяются при старте. Пароль БД не включается в строковое представление настроек и не возвращается через API.

## 6. Проверить замену модели без изменения frontend

В корневом `.env` замените строку:

```dotenv
PREDICTOR_FACTORY=app.predictors.constant:build_predictor
```

Перезапустите **backend**. Изменение `.env` не обязано автоматически запускать перезагрузку Uvicorn. Frontend менять или пересобирать не нужно. Повторный запрос покажет `model_version: constant-demo-v0`, значение 42 во всех точках и прочерки вместо отсутствующих границ.

Для возврата к суточным пикам:

```dotenv
PREDICTOR_FACTORY=app.predictors.mock:build_predictor
```

При Compose изменение настройки применяется командой из корня:

```bash
docker compose up -d --force-recreate backend
```

Будущая реальная модель реализует тот же `Predictor`. Примеры провайдеров находятся в `backend/app/predictors/`; отдельного модуля реальной модели пока нет.

## 7. Команды проверки

БД, из корня проекта, одинаково в PowerShell и Linux/macOS:

```bash
docker compose up -d --wait db
docker compose exec -T db sh /opt/transport/db/scripts/manage.sh status
docker compose exec -T db sh /opt/transport/db/scripts/manage.sh check
```

Ожидается `DB_CHECK_OK`. Для изолированной приёмки новой БД:

```bash
docker compose -f db/compose.test.yml up --force-recreate --abort-on-container-exit --exit-code-from check
```

Ожидается `DB_ACCEPTANCE_OK` и код завершения `0`. Рабочие данные не затрагиваются.
Подготовка Docker, сохранность volume и диагностика описаны в [docs/db.md](docs/db.md).

Backend, из `backend/`:

```bash
# Linux/macOS
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

```powershell
# Windows PowerShell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
```

Frontend, из `frontend/`:

```bash
npm ci
npm run build
```

Сборка включает проверку TypeScript. Результат — `frontend/dist`; папка не хранится в Git. `npm run preview` открывает собранное приложение на порту 4173 и также проксирует запросы к запущенному backend.

Обновить примеры и схемы после согласованного изменения API, из корня:

```bash
# Linux/macOS
backend/.venv/bin/python backend/scripts/export_contract.py
```

```powershell
# Windows PowerShell
.\backend\.venv\Scripts\python.exe backend/scripts/export_contract.py
```

В Python источником истины служат `backend/app/schemas.py`; TypeScript-описание находится в `frontend/src/types.ts`. При изменении контракта обновляются обе стороны и JSON-артефакты. Автоматическая генерация TypeScript пока не подключена.

`requirements.txt`, `requirements-dev.txt` и `package-lock.json` фиксируют проверенные версии зависимостей. Для запуска backend используется `requirements.txt`, а для разработки и тестов — `requirements-dev.txt`; frontend устанавливается через `npm ci`.

## 8. Если что-то не запускается

| Симптом                                                                   | Что проверить                                                                                                                                                   |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Address already in use`                                                       | Для локального режима нужны свободные порты 8000 и 5173; остановите прежний экземпляр приложения |
| Frontend открыт, но нет маршрутов                            | Откройте`/health` backend; проверьте `BACKEND_PROXY_TARGET`, после его изменения перезапустите Vite                      |
| `/health` возвращает 503                                             | При`CATALOG_BACKEND=postgres` проверьте БД и `POSTGRES_*`; для быстрого mock-запуска верните `memory`                         |
| `ModuleNotFoundError`                                                          | Запускайте команды из`backend/` Python-интерпретатором созданного `.venv`                                                   |
| `npm ci` или Vite сообщают о версии Node                     | Нужен Node 22.12+                                                                                                                                                      |
| Пример query отклоняется с 422                                 | Укажите часовой пояс, правильные границы сетки и кодируйте`+` в URL                                                    |
| После изменения seed в SQL ничего не поменялось | Инициализация Docker не запускается повторно на существующем volume; см. инструкции в`db/README.md`          |

## 9. Работа команды

`main` содержит рабочий интегрированный каркас. Отдельные задачи выполняются в `feature/<short-name>`. Перед объединением запускаются проверки затронутого сценария. Изменение общего JSON согласуется между backend, frontend и ML до merge.

Trello остаётся источником статусов задач; данный пакет сам по себе не изменяет карточки. Архитектурные договорённости находятся в `docs/architecture.md`, команды запуска — здесь, HTTP-контракт — в Pydantic/OpenAPI.
