# Отправка DB-задачи руководителю на ревью

По присланному Игорем выводу PostgreSQL 16.15 успешно запущен, таблицы и связи
проверены, данные сохранены после restart. Отчёт: [db-verification.md](db-verification.md).
Первые три задачи готовы к ревью. Команды ниже отправляют новую ветку;
объединение с `main` выполняет руководитель после просмотра Pull Request.

## 1. Подготовить файлы

Используйте последнюю версию `mt-transport-db-task1.zip`, в которой уже обновлён
отчёт Docker-проверки и присутствует этот документ. Код SQL и приложения после
успешного пользовательского прогона не менялся.

В архиве есть:

- `mt-transport-db/` — полная копия исходников для запуска;
- `db-task1.patch` — изменения только DB-задачи поверх подготовленного каркаса;
- `mvp-tasks1-3.patch` — первые три задачи поверх первоначального репозитория;
- `delivery.json` — SHA и состав изменений;
- `START_HERE.md` — краткая инструкция.

Не выполняйте `git init` в распакованной папке. Чтобы сохранить историю команды,
создайте новую рабочую копию актуальной `main`. Архив, `.bundle`, внешняя папка
поставки и вложенный Git-репозиторий не должны попасть в коммит.

## 2. Клонировать актуальную main и создать ветку

Откройте PowerShell. Команды рассчитаны на текущий путь проекта Игоря:

```powershell
cd "C:\Users\igorp\OneDrive\Desktop\Хакатон"
git clone --branch main https://github.com/hlpne/hackaton_asumadi.git hackaton-asumadi-db-review
cd hackaton-asumadi-db-review
git switch -c feature/i-reznik/db-schema
```

Выполняйте по одной команде. Если clone или switch завершились ошибкой, не переходите
к следующему шагу. Если папка `hackaton-asumadi-db-review` уже существует, используйте
другое свободное имя для нового клона; существующую папку удалять не нужно.

Если GitHub запросит вход, авторизуйтесь аккаунтом, которому выдали права записи.
Адрес должен быть именно HTTPS выше, без префикса `git@https`.

## 3. Применить подходящий патч

Путь ниже — папка, в которую распакован архив. Она содержит файлы `.patch`
и подпапку `mt-transport-db`. Если распаковали в другом месте, измените только путь:

```powershell
$packageDir = "C:\Users\igorp\OneDrive\Desktop\Хакатон\mt-transport-db-task1"

if (Test-Path "backend/app/main.py") {
    $dbPatchPath = Join-Path $packageDir "db-task1.patch"
} else {
    $dbPatchPath = Join-Path $packageDir "mvp-tasks1-3.patch"
}

git apply --check "$dbPatchPath"
```

Если каркас уже присутствует в main, выбирается DB-патч; если каркаса ещё нет —
патч первых трёх задач. Проверка `--check` ничего не изменяет. Отсутствие вывода
при коде завершения `0` означает, что патч применим.

```powershell
$LASTEXITCODE
```

**Только если результат `0`**, выполните:

```powershell
git apply "$dbPatchPath"
git status --short
git diff --stat
```

Патчи подготовлены относительно нашей исходной поставки. Если `--check` сообщает
`patch does not apply` или `already exists`, актуальная main отличается либо изменения
уже присутствуют. Не используйте force, не перезаписывайте проект архивом целиком:
потребуется сверить конкретные файлы с текущей версией команды. Сохраните текст ошибки.

## 4. Проверить состав и создать коммит

После применения должны быть доступны `docs/db.md`, `docs/db-verification.md`,
`db/scripts/manage.sh` и SQL-проверки. Посмотрите diff, особенно если в main уже
был каркас. Нормально, если `forecasts` по-прежнему пустая: постоянный demo seed
прогнозов входит в следующую задачу.

Добавьте только файлы проекта:

```powershell
git add -- backend frontend db docs mock_data docker-compose.yml README.md .env.example .gitignore .gitattributes .dockerignore
git diff --cached --name-status
git ls-files | Select-String '(^|/)\.env($|\.)'
```

Последняя команда должна вывести только `.env.example`. В staged-списке не должно
быть архивов, `.bundle`, `node_modules`, `.venv` или вложенного репозитория.
Если обнаружен уже отслеживаемый `.env`, сначала исключите его из индекса через
`git rm --cached -- .env`; локальный файл останется на компьютере.

```powershell
git commit -m "feat(db): finalize PostgreSQL schema documentation and checks"
git log -1 --oneline
git status --short
```

После коммита `git status --short` должен быть пустым. SHA вашего коммита может
отличаться от SHA в архиве: он создан поверх актуальной истории команды.
Успешные DB-проверки уже получены; повторяйте их, если пришлось изменять SQL,
Compose или скрипты при разрешении расхождений с main.

## 5. Отправить ветку

```powershell
git push -u origin feature/i-reznik/db-schema
```

Успех: Git сообщает об отправке новой ветки и настройке upstream. Если получите
`non-fast-forward`, не используйте `--force`: удалённая ветка уже имеет другую историю.
Для независимого ревью можно переименовать локальную ветку в свободное имя:

```powershell
git branch -m feature/i-reznik/db-schema-review
git push -u origin feature/i-reznik/db-schema-review
```

Этот вариант нужен только при конфликте имени/истории; при обычном успешном push
переименование не выполняйте. Ошибка `403` или `Repository not found` требует
проверки аккаунта и доступа к репозиторию, а не изменения истории Git.

## 6. Создать Pull Request

Откройте репозиторий команды и предложение **Compare & pull request** для отправленной
ветки. Проверьте:

- base: `main`;
- compare: `feature/i-reznik/db-schema` (либо имя после переименования).

Заголовок:

> MVP: схема PostgreSQL, документация и проверка БД

Описание для копирования:

```text
Подготовлена DB-часть MVP для независимой разработки API и интерфейса.

Состав:
- Четыре таблицы: routes, stops, route_stops, forecasts; ключи и ограничения.
- Подробная схема и команды запуска/тестирования в docs/db.md.
- Команды управления БД и изолированный сценарий приёмки.
- Настраиваемый внешний порт PostgreSQL и TCP healthcheck.
- Отчёт с результатами проверки в docs/db-verification.md.

Проверка на Windows PowerShell / Docker / PostgreSQL 16.15:
- Контейнер Healthy до и после restart.
- Таблицы созданы; количество строк 3 / 24 / 48 / 0 сохраняется.
- Все 31 SQL-проверка прошла; финальный маркер DB_CHECK_OK.

Принадлежность остановки маршруту/направлению проверяет backend;
SQL-внешние ключи проверяют существование объектов. Граница описана в docs/db.md.
Полноценный seed прогнозов относится к следующей задаче.
Прошу проверить изменения и объединить ветку после ревью.
```

Если применён `mvp-tasks1-3.patch`, добавьте в описание, что PR также содержит
ранее подготовленные архитектуру, ML-контракт и каркас backend/frontend.
Прикрепите исходный вывод проверки. Отдельный прогон `DB_ACCEPTANCE_OK` не заявляйте:
в предоставленном выводе присутствует `DB_CHECK_OK` для рабочей БД.

Проверьте вкладку **Files changed** и создайте PR. Merge оставьте руководителю.
